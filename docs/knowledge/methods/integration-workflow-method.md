# Integration Workflow

Provider integrations begin read-only. Credentials stay encrypted on the backend; clients receive only authentication type and configured/encrypted state. Each provider declares capabilities, status, structured errors, and last-sync state, and must implement connection testing, device discovery, and data pulling before it is registered as implemented.

Every connection list and connection write carries the active Personal, Commercial, or Facility workspace scope. Personal and Commercial ownership resolves to the authenticated account; Facility ownership resolves to the selected authorized Facility and permits setup writes only for owners and managers. A connection from one workspace must never appear as an available connection in another workspace merely because the same human can enter both. A Facility identifier is an ownership boundary, never a substitute grow target.

Connection methods are provider-specific and must not be collapsed into a generic claim. Pulse, ZENTRA and UbiBot accept customer-managed keys or tokens. TrolMaster accepts a customer developer key only after the customer has requested per-device API access and subscribed that key to the relevant API; until the signed-in endpoint contract is verified, GrowPath may store the encrypted key but must show that device discovery is still awaiting provider access. Growlink uses its reviewed account flow. SensorPush and Tempest require production OAuth work. Monnit requires a key ID plus secret. Home Assistant requires a reviewed URL plus dedicated token. AC Infinity and Bluelab/Edenic currently use history-file import. Davis WeatherLink uses a customer API key plus secret and may require Pro/Pro+ for historical readings. Ecowitt supports a customer cloud API path and a separately reviewed local-network HTTP path. Rachio uses the customer's bearer API key. Shelly supports cloud and local-device APIs. Particle devices can push owner-authorized events through webhooks. OpenSprinkler and Agrowtek are local/gateway connections and remain read-only until local-network security and protocol validation are complete.

Setup is review gated: select provider, connect, test, fetch structure, preview devices and metrics, edit space/room/zone mappings, then confirm. Auto-build is a separate explicit action after confirmation and must be idempotent. The same reviewed workflow is available from Grows for Personal, Commercial, and Facility workspaces. A shared imported space can represent a room, tent, greenhouse, bed, or outdoor area; only Facility mode also creates a canonical Facility room. Never create or rename a space from an unreviewed provider guess.

Personal auto-build targets an owned grow and creates read-only spaces, devices, streams, and dashboard definitions. Facility auto-build requires owner or manager access and creates canonical rooms plus read-only devices/streams and draft alert/dashboard definitions. Commercial auto-build targets only owned product-trial evidence runs or grows explicitly intended for trials, demos, or education; it must not turn ordinary storefront or campaign records into cultivation spaces. Personal and Commercial imported spaces are durable grow-owned records rather than simulated Facility rooms.

Every built space preserves the connection, provider, provider device ID, reviewed space and zone names, metrics, confirmation time, last build time, and read-only permission. Rebuilding the same provider space updates that record instead of duplicating it. CSV or provider history must be saved to the selected grow/evidence run and must preserve source timestamps and raw provider fields; a device map by itself is not imported history.

File history import is also review gated. Read a selected native document URI when the device runtime supplies one, while retaining paste as a fallback. Personal Data Integrations must expose the same reviewed importer already used by Commercial and Facility workspaces after an owned grow is selected. Accept at most 25 MB per CSV and at most 5,000 normalized rows per import; ask for a shorter provider export instead of silently retaining a larger file. Before source creation or ingestion, show and confirm the detected provider, active workspace, exact grow, reviewed room or space, IANA timezone, bounded file identity, and column mapping. Store that review as provenance without retaining a device-local URI. An AC Infinity export may enter only an AC Infinity upload source with the same workspace, grow, room, and timezone; never append it to Pulse, Growlink, manual, generic, or another provider source. Reimporting the same source timestamp uses the idempotent update path rather than creating a duplicate point.

An exported column named `LIGHT` is not evidence that the setup had an illuminance sensor. The import review must distinguish measured illuminance in an explicit provider-supplied unit from controller-reported lighting on/off or output state and from an unknown raw provider value. Preserve the raw value and the reviewed meaning, never convert controller state to lux, and never claim measured brightness when the user reports that no light detector was installed. A sparse export may support only timestamped state snapshots; it cannot reconstruct every transition, schedule, or lights-on duration. Owner confirmation recorded 2026-08-25 establishes that the reviewed AC Infinity QA export used here had no light detector and that its `LIGHT` column represented lighting state/output for this setup; do not universalize that statement to other devices or exports without review.

Light-sensor channels remain separate from controller state. A reviewed sensor or provider export may supply measured illuminance in lux, PPFD in umol/m2/s, or DLI in mol/m2/day; preserve each under its own canonical metric and source unit, and never substitute one for another without an evidence-backed conversion. The current owner-reported QA equipment context is two Mars Hydro FC-E4800 fixtures in one 4 x 8 space. That model and count may be retained as equipment context, but they do not establish measured canopy PPFD, DLI, uniformity, hanging height, dimmer output, photoperiod, or light-leak status without reviewed readings and setup details.

A normalized environment point requires a nonblank mapped timestamp, inside temperature, and inside relative-humidity value. Do not coerce an empty mapped cell to numeric zero merely because another outside or optional channel is present on that row. Skip the incomplete point, keep the source row count distinct from the normalized point count, and report the resulting ingest/skipped receipt truthfully.

Cloud-history import is an explicit action after the reviewed spaces exist. The user chooses a bounded 7-, 30-, or 90-day window, while the API permits reviewed windows up to 366 days. Each provider device receives an idempotent grow-owned telemetry source linked to the connection and built space. Reimporting a timestamp updates that source record rather than duplicating it. The sync receipt must report devices attempted, device failures, pulled normalized snapshots, inserts, updates, range, and provider. A partial provider failure remains visible as failed sync state; successful devices must not be reported as a wholly successful import.

Personal Data Integrations are grow-owned discovery. Surface connection and mapping entry points from Grows and the selected grow workspace, not from the general AI Tools hub. Preserve old deep links, but validate every deep-linked grow against the current workspace's owned-grow list before exposing provider mapping or telemetry actions. User-facing setup must offer named owned-grow choices rather than asking a person to type an internal grow identifier. Require an owned grow before saving imported structure or telemetry.

Provider metric keys remain source evidence. Normalization must preserve the provider key alongside the canonical metric and must not invent units, readings, thresholds, room identity, or control capability. Controller writes, setpoints, schedules, and automation activation require a separately reviewed permission scope.

Canonical metrics are `air_temperature` in C, `relative_humidity` in percent, `vpd` in kPa, `dew_point` in C, `co2` in ppm, `ppfd` in umol/m2/s, `dli` in mol/m2/day, `substrate_moisture` in percent, `substrate_ec` in mS/cm, `substrate_ph` in pH, plus `irrigation_event`, `alarm`, `device_offline`, and `device_fault` state/event signals. Convert Fahrenheit/Kelvin, fractional moisture/RH, or uS/cm only when the provider supplies that source unit. Unknown keys remain `unmapped` with their raw evidence intact.

All tool handoffs use the same grow-scoped telemetry window. It may deterministically prefill VPD, dew point, Bud Rot screening, Crop Steering, Watering Planner/dryback, AI context, run comparisons, alert/task drafts, and explicitly linked trial evidence. Bud Rot output is a screening signal, not a diagnosis. Alerts and tasks remain drafts until reviewed. Course examples require explicit review and de-identification; telemetry must never be published merely because it was imported.

Do not add a collected integration field without declaring at least one concrete consumer in the integration data-use registry. Allowed consumer categories are display, analytics, AI, search, recommendations, tasks, alerts, and exports. Schema audits must fail when a governed field is missing, stale, or assigned an unsupported category. Credential values remain secret; their collected field supports derived configured/encrypted display state and must never be returned as registry data or ordinary exports.
